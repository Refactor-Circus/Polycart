# Polycart

This repository is a Laravel package. Keep the package focused, idiomatic, and easy for Laravel developers to install, test, and maintain.

## Package Conventions

- Use Laravel-native package APIs and the existing service provider shape before adding abstractions.
- Keep package names, namespaces, Composer metadata, publish tags, documentation, and examples aligned with `refactor-circus/polycart`.
- Add only the files and dependencies needed for the package behavior being implemented.
- Prefer explicit Laravel package code over helper abstractions unless the extension point is real.
- Keep tests focused on observable package behavior through public APIs, service provider wiring, commands, routes, published resources, and documentation promises.

## Architecture

- Code lives in domain modules under `src/Domains/{Domain}` (Cart, CartLine, CartType, Sharing, Scope), mirroring the `mono` domain-module standard. Each domain has a `{Domain}ServiceProvider` (extending `RefactorCircus\Keystone\Support\ServiceProvider`) registered by `src/Domains/DomainServiceProvider.php`, its own `routes.php`, and only the subdirectories it uses.
- Polycart stands on `refactor-circus/keystone`, the shared runtime of the Refactor Circus suite. `PolycartServiceProvider` extends `RefactorCircus\Keystone\Support\PackageServiceProvider`: it describes the package in `definition()` (`Package::make('polycart', ...)->authorization()`, so authorization defaults to on), calls `registerPackage()` right after merging config, and uses the base helpers for policies, the MCP server, Cortex, the Atrium plugin and the `GET {prefix}/history` route. Do not copy Keystone classes back into the package; if Keystone lacks something, add a thin local subclass.
- Use Keystone's classes directly: event contracts (`RefactorCircus\Keystone\Contracts\*`), `Models\Concerns\DispatchesModelEvents`, `Http\Requests\Request`, `Mcp\Tool`, `Mcp\Server`, `Auth\Authorizer` (`Authorizer::for(app(PackageRegistry::class)->get('polycart'))`) and `Cortex\CortexIntegration`. `PolycartException` extends `PackageException` with status 422, and the base policy extends Keystone's `Policy` (`allowsOn()`).
- MCP requests extend `RefactorCircus\Polycart\Mcp\Request`, which extends Keystone's and implements `handle()` to keep the `cortex` surface for agent calls and add line reason codes; each request implements `respond(array $validated)`.
- Action input is a `final readonly` `{Action}Data` in the domain's `Data/` (on `RefactorCircus\Keystone\Data\Data`), never an array: fields are promoted constructor properties (camelCase of the input keys; enums for enum values; `T|Missing = new Missing` for partial updates), `rules()` lives on the Data, and the starting events that took input carry the Data. Models a call names - an owner, scope, member or the cart merged into - are resolved by the request through `Support\Morphs` (whose `ownerRules()`, `scopeRules()` and `memberRules()` are the identifier rules) and passed to the Action beside its Data; batch lines are `AddLinesData`/`UpdateLinesData`/`RemoveLinesData` holding `AddLineData`/`LineChangeData` entries (`#[ListOf]` fields, built item by item), and `AddLineData::prepare()` finds each purchasable through `polycart.purchasables`. HTTP and MCP requests validate once: their `rules()` return the identifier rules plus `XData::rules()` (identifiers first, so they win; MCP cart requests start from `cartRules()`), and `persist()`/`respond()` build with `XData::fromValidated($this->validated() / $validated)` - never `XData::from()` in a request (ArchTest). Atrium controllers use `XData::from($request->all())`, which validates; code that vouches for its values (the facade, `CartModel`'s helpers) uses `new XData(...)`. Every Action's writes run in one transaction (the injected `ConnectionInterface`'s `transaction()`; an Action that combines other Actions wraps them in one too), with the starting event dispatched before it and the finished event after, so a rollback finishes nothing. `tests/ArchTest.php` rejects array input on `execute()` and checks every Action dispatches a starting and a finished event, writes inside a transaction, and every model fires an event for every Eloquent hook (Keystone's `Testing\Arch`: `actionEventGaps()`, `writesOutsideTransactions()`, `modelEventGaps()`; `parityGaps()` uses `Testing\Parity`).
- Batch line Actions (`AddLinesAction`, `UpdateLinesAction`, `RemoveLinesAction`, `ClearCartAction`, `MergeCartsAction`) run their per-line Actions inside `$cart->batchLines()`, so the cart's lifetime is extended once and new positions are counted in memory; batches find their lines with `LineLookup::lock()` (one locking read), and `lines()`/`members()` are chaperoned so each child holds the cart instance it came from. `ScopeTree` is a `scoped()` binding that reads what each actor reaches once per request (`forget($actor)` after changing someone's scopes mid-request). `tests/Feature/PerformanceTest.php` keeps query budgets for these paths.
- Batch line Actions (`AddLinesAction`, `UpdateLinesAction`, `RemoveLinesAction`, `ClearCartAction`, `MergeCartsAction`) run their per-line Actions inside `$cart->batchLines()`, so the cart's lifetime is extended once and new positions are counted in memory; batches find their lines with `LineLookup::lock()` (one locking read), and `lines()`/`members()` are chaperoned so each child holds the cart instance it came from. `ScopeTree` is a `scoped()` binding that reads what each actor reaches once per request (`forget($actor)` after changing someone's scopes mid-request). `tests/Feature/PerformanceTest.php` keeps query budgets for these paths.
- API resources extend `RefactorCircus\Keystone\Http\Resources\JsonResource` and declare `schema(JsonSchema $schema)` next to `toArray()` (always-present fields `required()`, conditional ones not, `nullable()`, enum values listed; nullable enums include `null`); nested resources are resolved to arrays. MCP requests answer with `(new XResource($m))->toStructuredResponse()` / `XResource::collection($page)->toStructuredResponse()`, and each tool declares `outputSchema()` as `XResource::structuredSchema($schema)` / `collectionSchema($schema, ListXData::pagination())`, or a hand-written schema for a plain answer. `mcpTool()` / `mcpToolAs()` in tests are Keystone's `Testing\McpTools::call()`, which checks every structured answer against the tool's schema, and `tests/Feature/Mcp/OutputSchemaTest.php` requires the declaration. Missing records on the JSON API answer a plain `{"message": "Not found."}` (`registerNotFoundResponses()`), and guests get 401.
- History belongs to refactor-circus/keen, the suite-wide audit log; Polycart keeps none of its own and must not grow a parallel log. A cart's `source` column is Keystone's `Surface::current()` when it is created or converted. Action events whose first model is not the right subject implement `RefactorCircus\Keystone\Audit\Contracts\Auditable` (line, sharing, merge and conversion events name the cart); carts and lines get `AuditHooks` labels from their domain providers, registered once every provider has booted and only while Polycart audits: Keystone's `Package::audits()` (refactor-circus/keen installed and `polycart.audit.enabled` on). Otherwise Keen ignores Polycart's events, the history route answers 404 and the history tool is not offered. Screens show history with `<x-atrium::audit-trail source="polycart" ... />`.
- Models are named `{Entity}Model`; their pre-domain class names are kept as morph aliases in each domain provider. Model events derive from `{Entity}{Hook}Event` in the model's domain `Events` namespace. Models resolve their table with `getTable()` from `Support\Tables` (`polycart.tables`, on Keystone's `Database\Tables`); the migration's `Schema` calls and `constrained()` foreign keys use the same keys, never literal `polycart_*` names, and the rows the cart's model hooks write (paths, the owner's membership) go through the relations so they follow the configured tables (`tests/ArchTest.php` checks with `Arch::literalTableNames()`, and `tests/Modes/RenamedTables` reruns representative flows against renamed tables). Every model has a policy (`Domains/{Domain}/Policies`, on `Support\Policies\Policy`) in `polycart.policies`, registered by `registerPolicies()`; child models (lines, members, paths) ask about their cart with `allowsOn()` (`Arch::modelsWithoutPolicies()` checks the config).
- Cross-domain code stays outside the domains: `Polycart`, the facade, `Mcp\Request`, `PolycartServer` and `Mcp\Tools\ListPolycartHistoryTool`, `Support/` (`Morphs`, `Tables`, `Policies\Policy`), and `Atrium/` (dashboard screens, `ScreenAccess`, `PolycartSupportFeature`).
- Atrium owns every component and style: Polycart ships no stylesheet, and views use only `x-atrium::*` components and the utilities Atrium safelists, never `<style>` or `style=`. `tests/Feature/Ui/StylesTest.php` checks both with `AtriumStyles`. `ScreenAccess` delegates to Atrium's `ScreenAccess::allows('polycart', ...)` and keeps only what is Polycart's own: operators and abilities with arguments.
