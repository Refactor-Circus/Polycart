# Polycart

This repository is a Laravel package. Keep the package focused, idiomatic, and easy for Laravel developers to install, test, and maintain.

Polycart is API plus MCP: a JSON API (off by default, `polycart.routes.enabled`) and an MCP server over the same actions, plus its own Atrium front-end module. Atrium v2 is the optional UI, a separate package; Polycart ships only the module's JavaScript (Vue sources in `atrium/`, built into the committed `dist/atrium/`, declared in `composer.json`'s `extra.atrium`), which Atrium injects into its page and which calls the JSON API through the committed `openapi.json` and the TypeScript client in `client/`.

## Package Conventions

- Use Laravel-native package APIs and the existing service provider shape before adding abstractions.
- Keep package names, namespaces, Composer metadata, publish tags, documentation, and examples aligned with `refactor-circus/polycart`.
- Add only the files and dependencies needed for the package behavior being implemented.
- Prefer explicit Laravel package code over helper abstractions unless the extension point is real.
- Keep tests focused on observable package behavior through public APIs, service provider wiring, commands, routes, published resources, and documentation promises.

## Architecture

- Code lives in domain modules under `src/Domains/{Domain}` (Cart, CartLine, CartType, Sharing, Scope), mirroring the `mono` domain-module standard. Each domain has a `{Domain}ServiceProvider` (extending `RefactorCircus\Keystone\Support\ServiceProvider`) registered by `src/Domains/DomainServiceProvider.php`, its own `routes.php`, and only the subdirectories it uses.
- Polycart stands on `refactor-circus/keystone`, the shared runtime of the Refactor Circus suite. `PolycartServiceProvider` extends `RefactorCircus\Keystone\Support\PackageServiceProvider`: it describes the package in `definition()` (`Package::make('polycart', ...)->authorization()`, so authorization defaults to on), calls `registerPackage()` right after merging config, and uses the base helpers for policies, the MCP server, Cortex, the `GET {prefix}/history` route and the not-found responses. It publishes only the config and the migrations, and loads no views or translations. Do not copy Keystone classes back into the package; if Keystone lacks something, add a thin local subclass.
- Use Keystone's classes directly: event contracts (`RefactorCircus\Keystone\Contracts\*`), `Models\Concerns\DispatchesModelEvents`, `Http\Requests\Request`, `Mcp\Tool`, `Mcp\Server`, `Auth\Authorizer` (`Authorizer::for(app(PackageRegistry::class)->get('polycart'))`) and `Cortex\CortexIntegration`. `PolycartException` extends `PackageException` with status 422, and the base policy extends Keystone's `Policy` (`allowsOn()`).
- MCP requests extend `RefactorCircus\Polycart\Mcp\Request`, which extends Keystone's and implements `handle()` to keep the `cortex` surface for agent calls and add line reason codes; each request implements `respond(array $validated)`.
- Action input is a `final readonly` `{Action}Data` in the domain's `Data/` (on `RefactorCircus\Keystone\Data\Data`), never an array: fields are promoted constructor properties (camelCase of the input keys; enums for enum values; `T|Missing = new Missing` for partial updates), `rules()` lives on the Data, and the starting events that took input carry the Data. Models a call names - an owner, scope, member or the cart merged into - are resolved by the request through `Support\Morphs` (whose `ownerRules()`, `scopeRules()` and `memberRules()` are the identifier rules) and passed to the Action beside its Data; batch lines are `AddLinesData`/`UpdateLinesData`/`RemoveLinesData` holding `AddLineData`/`LineChangeData` entries (`#[ListOf]` fields, built item by item), and `AddLineData::prepare()` finds each purchasable through `polycart.purchasables`. HTTP and MCP requests validate once: their `rules()` return the identifier rules plus `XData::rules()` (identifiers first, so they win; MCP cart requests start from `cartRules()`), and `persist()`/`respond()` build with `XData::fromValidated($this->validated() / $validated)` - never `XData::from()` in a request (ArchTest). Code that takes untrusted input outside a request uses `XData::from($input)`, which validates; code that vouches for its values (the facade, `CartModel`'s helpers) uses `new XData(...)`. Every Action's writes run in one transaction (the injected `ConnectionInterface`'s `transaction()`; an Action that combines other Actions wraps them in one too), with the starting event dispatched before it and the finished event after, so a rollback finishes nothing. `tests/ArchTest.php` rejects array input on `execute()` and checks every Action dispatches a starting and a finished event, writes inside a transaction, and every model fires an event for every Eloquent hook (Keystone's `Testing\Arch`: `actionEventGaps()`, `writesOutsideTransactions()`, `modelEventGaps()`; `parityGaps()` uses `Testing\Parity`).
- Batch line Actions (`AddLinesAction`, `UpdateLinesAction`, `RemoveLinesAction`, `ClearCartAction`, `MergeCartsAction`) run their per-line Actions inside `$cart->batchLines()`, so the cart's lifetime is extended once and new positions are counted in memory; batches find their lines with `LineLookup::lock()` (one locking read), and `lines()`/`members()` are chaperoned so each child holds the cart instance it came from. `ScopeTree` is a `scoped()` binding that reads what each actor reaches once per request (`forget($actor)` after changing someone's scopes mid-request). `tests/Feature/PerformanceTest.php` keeps query budgets for these paths.
- API resources extend `RefactorCircus\Keystone\Http\Resources\JsonResource` and declare `schema(JsonSchema $schema)` next to `toArray()` (always-present fields `required()`, conditional ones not, `nullable()`, enum values listed; nullable enums include `null`); nested resources are resolved to arrays. MCP requests answer with `(new XResource($m))->toStructuredResponse()` / `XResource::collection($page)->toStructuredResponse()`, and each tool declares `outputSchema()` as `XResource::structuredSchema($schema)` / `collectionSchema($schema, ListXData::pagination())`, or a hand-written schema for a plain answer. `mcpTool()` / `mcpToolAs()` in tests are Keystone's `Testing\McpTools::call()`, which checks every structured answer against the tool's schema, and `tests/Feature/Mcp/OutputSchemaTest.php` requires the declaration. Missing records on the JSON API answer a plain `{"message": "Not found."}` (`registerNotFoundResponses()`), and guests get 401.
- History belongs to refactor-circus/keen, the suite-wide audit log; Polycart keeps none of its own and must not grow a parallel log. A cart's `source` column is Keystone's `Surface::current()` when it is created or converted. Action events whose first model is not the right subject implement `RefactorCircus\Keystone\Audit\Contracts\Auditable` (line, sharing, merge and conversion events name the cart); carts and lines get `AuditHooks` labels from their domain providers, registered once every provider has booted and only while Polycart audits: Keystone's `Package::audits()` (refactor-circus/keen installed and `polycart.audit.enabled` on). Otherwise Keen ignores Polycart's events, the history route answers 404 and the history tool is not offered. A front end shows a cart's history from the history route.
- Models are named `{Entity}Model`; their pre-domain class names are kept as morph aliases in each domain provider. Model events derive from `{Entity}{Hook}Event` in the model's domain `Events` namespace. Models resolve their table with `getTable()` from `Support\Tables` (`polycart.tables`, on Keystone's `Database\Tables`); the migration's `Schema` calls and `constrained()` foreign keys use the same keys, never literal `polycart_*` names, and the rows the cart's model hooks write (paths, the owner's membership) go through the relations so they follow the configured tables (`tests/ArchTest.php` checks with `Arch::literalTableNames()`, and `tests/Modes/RenamedTables` reruns representative flows against renamed tables). Every model has a policy (`Domains/{Domain}/Policies`, on `Support\Policies\Policy`) in `polycart.policies`, registered by `registerPolicies()`; child models (lines, members, paths) ask about their cart with `allowsOn()` (`Arch::modelsWithoutPolicies()` checks the config).
- Cross-domain code stays outside the domains: `Polycart`, the facade, `Mcp\Request`, `PolycartServer` and `Mcp\Tools\ListPolycartHistoryTool`, and `Support/` (`Morphs`, `Tables`, `Policies\Policy`).
- Stats and search serve what a front end's overview and search box need. `GET {prefix}/stats` (`polycart.stats.show`, `CartController::stats` through `ShowCartStatsRequest`) and the `cart-stats` MCP tool (`CartStatsTool` through `ShowCartStatsMcpRequest`) run `ShowCartStatsAction::execute(?Model $viewer)`: one grouped count of the viewer's accessible, unexpired carts per registered type (zero-filled, registry order) and one read of the 5 most recently updated accessible carts with `lines_count`, returned as `Support\CartStats` and shaped by `CartStatsResource` (`{"data": {"by_type": [{type, count}], "recent": [CartResource]}}`). `GET {prefix}/search?q=` (`polycart.search.index`, `SearchCartsRequest`) adds no action: it runs `ListCartsAction` with the `search` filter and answers as `polycart.carts.index` does; MCP searches through `list-carts`'s `search`. Both need `viewAny` on `CartModel`. `tests/Feature/StatsTest.php` keeps the stats query count flat.
- The JSON API is described by the committed root `openapi.json` and called through the TypeScript client in `client/` (`@refactor-circus/polycart-client`: `createPolycartClient()` around openapi-fetch, TypeScript source with no build step, export-ignored from the Composer dist). `dedoc/scramble` is require-dev only and `src/` never uses it (`tests/ArchTest.php`): the workbench's `workbench:openapi {path}` (`ExportOpenApiCommand`, in-memory SQLite, fixed `/polycart` server and version 2.0.0) exports the document, and `WorkbenchServiceProvider` makes each resource listed in its `RESOURCES` the component schema of its own `schema()`. After changing a route, request or resource, run `composer client:generate` (needs Node): it exports `openapi.json`, runs `npm --prefix client ci` and `npm --prefix client run generate` (writes `client/src/schema.d.ts` and `client/openapi.sha256`); commit all three. `tests/Feature/OpenApiTest.php` is the staleness test (a fresh export must equal `openapi.json`, and the stamp must be its SHA-256), and the CI `client` job regenerates, runs `git diff --exit-code -- openapi.json client` and type-checks the client.
- Polycart ships no PHP UI: no views, translations, Blade or Atrium PHP classes. Its front end is its Atrium module, JavaScript only: Vue sources in `atrium/` (export-ignored; built with the Atrium SDK's Vite preset, the SDK a dev dependency pinned to a commit in `atrium/package.json`), built into the committed and shipped `dist/atrium/` (`atrium.js`, `chunks/`, `atrium.css`, `build.json`) and declared in `composer.json`'s `extra.atrium`. Pages use `client/src/schema.d.ts` for their types and Atrium's signed `useAtriumIntegration('polycart')` client. After changing `atrium/` or the client, rebuild with pnpm 10 (`cd atrium && pnpm install && pnpm typecheck && pnpm test && pnpm build`) and commit `dist/atrium/`: `tests/Feature/AtriumModuleTest.php` fails on a build older than its sources (the `build.json` hash), and the CI `ui` job rebuilds and diffs. No PHP names Atrium: `tests/ArchTest.php` forbids `RefactorCircus\Atrium` classes, Composer neither requires nor suggests it, and `tests/Feature/NoAtriumTest.php` scans the code, config, routes, workbench and build files, allowing only the `extra.atrium` block, the `/atrium` export-ignore and the `ui` workflow. `polycart.routes.enabled` stays off by default; the workbench turns it on.
